# 实现期间的选择

已定事项在 [README.md](README.md)。这里只记规格没写死、由实现定下来的事。一条记录不是改规格的放行：规格已经写了的，先改规格再改代码。银行里的条目不再重列，收尾时对照最终代码重写本文件。

信心低的排在前面。

## 01 协议夹具

### 已定，按这个做

- **上游回复的夹具是一条 Chat JSON，不是 magpie 真正收到的 SSE。** 本档的文件必须是 JSON。magpie 翻译时会强制上游流式，非流式正文它直接报错，所以抄不到一份「上游 HTTP 正文」。请求侧的上游字节是对 magpie 的实测；回复侧是按同一次对话拼出的 `chat.completion`，译回 Anthropic 后与 magpie 非流式渲染的字节一致（思考、正文、一次工具调用、用量 10/5）。信心：中。以后的流式解码不要把这份 JSON 当成上游线上的事件序列。

- **缺了的 id 留空，不按时钟现编。** magpie 会给空的工具调用 id 编 `call_`、给空的消息 id 编 `msg_`。本档夹具里的 id 都有值。现编会让同一份输入每次字节不同。Agent 没给 id 时，译出的 id 就是空字符串。信心：中。

- **一条回复只译 `choices` 里的第一条。** magpie 的翻译也只锁定第一条能读的 choice。夹具只有一条。后面的 choice 被丢掉。信心：中。

- **Anthropic 译成的 Chat 请求总是要求流式，并带上用量。** 不看 Agent 有没有写 `stream`。上游正文带 `stream: true` 和 `stream_options.include_usage`。这是 magpie `translate()` 拼上游之前的做法；入站有没有 `stream`，实测上游字节相同，也和本档夹具一致。信心：高。后面的保持写者可以假定上游回的是流。

- **工具的 `input` 和 `input_schema` 按 Agent 写下的字节复制。** 用的是 `serde_json` 的 `raw_value`，没有开 `preserve_order`。后者会改掉整个 workspace 的对象键顺序。`raw_value` 只是解析接口，不会让别的 crate 换一种编码。不能把 `RawValue` 放进 untagged enum，serde 会先缓冲成 `Value`，原始字节就丢了。信心：高。

### 琐碎

- 夹具文件末尾多一个换行会在比较前丢掉。允许表目前只实现 `brand`（先替换 `Magpie`，再替换 `magpie`）。未知规则直接让测试失败。这些 JSON 是字节夹具，不进 biome 格式化，和 `tool_sync` 的 golden 一样。

## 02 首内容字节

### 已定，按这个做

- **超过 15 秒之后，下一拍如果是错误，仍然不放给 Agent。** 规格说等到超过 15 秒就放行。magpie 先看这一拍是不是错误或内容，再看时间和体积。所以时钟已经超过 15 秒、但还没有任何内容时，下一拍若是错误，字节留在下游之外，调用方可以换上游；下一拍若只是 `ping`，才放行。放行之后的错误才会到达 Agent。信心：中。

- **这个写者只认事件流，不认 HTTP 状态码。** 非流式的 500 还没有地方可放。等真正监听、响应头进到这里时再接。在那之前，调用方不要把普通 HTTP 错误正文塞进 `HoldWriter` 当作已经会换上游。信心：中。

- **「内容之前出错了」和「这段错误该休息多久」分开。** 本档只要错误事件出现在内容之前，就报告 `failed_before_content`。一条 400 是不是请求自己写错，词表在 11 档。本档夹具里的错误都是 magpie 会交给下一个上游的那种（过载、`response.failed`、`upstream failed`）。信心：中。

- **规格点名之外，还有两种也不当内容或当作内容。** `: keep-alive` 这种 SSE 注释不是内容。`data: [DONE]` 解析不成 JSON，算内容，否则 Chat 流的结尾会被当成还能换。Chat 块里出现 `finish_reason` 也算内容，哪怕正文是空的。信心：高。

- **计时从第一字节开始，不是从写者造出来开始。** 这个类型没有响应头。magpie 是在看到 `text/event-stream` 时开始计时，这里用第一字节代替。测试要先写入，再拨时钟。信心：高。

## 03 一条路由决定

### 先这样，09 档再看

- **同一档内部保持调用方给的顺序。** 用量不到 98 的排在前面，没有快照的排在中间，达到 98 的排在后面。档内不再按用量从低到高排，也不把 90 划成单独一档，也不按重置时间排。magpie 的空字符串模式会做后两件事。本档规格只要求这两道分界。09 档钉 smart 的完整夹具时可以在档内再排，只要「98 靠后」和「unknown 不是耗尽」还在。信心：中。

## 04 环回监听

### 先这样，后面的档再接

- **这一档的 Chat 把上游正文读完再交回去，不经过保持写者。** 夹具是一整份 JSON。监听已经能把字节原样送上去、再原样送回来。流还没接到「首内容字节之前可以换上游」。等会换上游的那一档再把保持写者放进这条路径。信心：中。

- **除了 `POST /v1/chat/completions`，其它路径都是 404。没有配上游时，这条路径是 502。** 规格这一档只要求这一条 Chat。状态码它没写。08 档铺开路由表时会换掉这些 404。信心：中。

- **一个连接上不等待的第二条请求，不按空闲重新计时。** 响应还没标记完成时，已经缓冲进来的下一份请求头会算在正文阶段里，5 分钟的空闲不会从它的第一字节开始。常见客户端会等这一份响应再发下一份。规格没要求管道化。信心：中。

### 已定，按这个做

- **等响应头的 10 分钟把建立连接的时间也算进去。** `send` 要等连接完成才等得到头，截止时间包住这一整段。连接自己还有 10 秒的上限，所以慢连接不会真的占满 10 分钟。信心：中。

- **流式客户端的空闲连接跟短探测共用一套数：空闲 90 秒，每个主机最多留 4 条。** magpie 的流式传输是每个主机 8 条。规格要求同一份代理指纹，没有要求再维护一套池大小。两套数会让「走不走代理」和「留几条连接」分成两处。信心：中。

- **请求正文和响应正文没有读超时。** 只有读头 30 秒，以及两次请求之间的空闲 5 分钟。长回复如果被读超时切断，流就断在半截。规格点了这两个时间，没有点正文时间。信心：高。

- **地址解析失败就是错误。** 空的环境变量用默认地址。写错的地址不回退到默认，也不做 DNS。监听要的是 `IP:端口`。信心：高。

- **`skillstar gateway` 在打开 CLI 的迁移之前就返回。** 规格要求它不打开窗口。普通 CLI 入口会先做路径迁移和商店快照初始化，那会碰本机数据目录。只为了听一个端口，不跑那一步。`skillstar help` 仍能列出这个子命令。`gateway` 后面如果不是正好一个 `serve`，用法写到 stderr。信心：高。
